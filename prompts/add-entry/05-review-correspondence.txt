Read README.md, formal/README.md, docs/verification-and-review.md, the entire
entry, all linked node records and descriptions, and the actual target declarations.
Inspect referenced definition bodies and the checked signatures in current verification
evidence. Do not assume a prior AI's mapping or a passing Lean build is correct
evidence of correspondence.

1. Make a coverage table by block: human definitions/claims, covering node IDs,
   any specialization or representation bridge, and gaps. Include examples,
   question answers, counterexample witnesses, prose claims, and empty/boundary
   cases. Explain each empty mapping; distinguish it from an unplanned block.
2. Compare each node description with its actual declaration and the human text.
   Descriptions should state the result or object, not merely name the topic, omit
   assumptions, or introduce unproved claims. They are editable editorial aids,
   excluded from target hashes, so an accepted declaration does not certify its
   description. Compare hypotheses, quantifiers, logical directions, conclusions,
   and domains.
   Check existence as well as uniqueness, both inverse laws for the same inverse,
   the surrounding set for complements, and the declared codomain for surjectivity
   and composition. Verify relevant conventions, including total operations in
   Lean that are partial in the prose, subtypes, and finite-cardinality functions.
   Stronger or more general library statements are valid bindings when their
   specialization covers the text; record that specialization explicitly.
3. Search for unnecessary local wrappers and opportunities to reuse built-in Lean
   or mathlib declarations and existing nodes. Find duplicate targets, redundant
   directions of equivalences, and repeated coverage of the same claim. For each
   proposed removal, explain why all human claims remain covered. Do not call an
   explicitly stated example or distinct reformulation redundant merely because
   it follows from earlier mathematics. Check why each linked node is useful.
4. Review dependencies as proof prerequisites only. They do not encode reading
   order, every concept in a statement, or block coverage. Identify unnecessary
   edges, cycles, and missing planned prerequisites without recreating mathlib's
   entire dependency graph. Keep this distinct from actual Lean axiom dependencies.
5. Inspect current source locations and elaborated signatures. A generated target
   may point to a differently named source origin, and the defining module may
   differ from the import module. Neither alone establishes a binding error.
   For non-obvious conversions, use small temporary Lean checks outside the tracked
   source tree; do not prove pending production theorems during this review.

Return findings with concrete file/block/node references and suggested changes,
then the coverage table and checks performed. Distinguish wrong statements,
uncovered claims, implicit representation bridges, and optional simplifications.
Identify exactly which nodes would need new review if suggestions are applied.
Do not change bindings or review records during this audit.
